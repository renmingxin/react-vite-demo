### 1\.运行态\-全部审批动作的开发与维护\(20\+按钮\)

- **S（业务背景）**：在运行态最核心的能力就是当用户在审批工作台页面的时候操作一张表单单据在审批流转过程中，每个处理人看到并操作的一整套审批流程，包括了发送、提交、统一、回退、知会、加签、会签、取回、撤销、终止等一些列审批动作，一共二十多类，当时没有一个统一清晰的架构，还停留在这些审批按钮动作UI需要自己写并且UI的视图代码还在我们bpm这边维护的臃肿状态，后面我接手的时候第一时间就觉得这套东西只需要我们这边抽象为一个触发后执行的抽象方法或组件就行了

- **T（任务难点）**：把审批动作的触发方式不在依赖UI层，跟其他上下游组达成沟通共识，为了推进此次改进计划最主要的是跨部门的沟通，然后用监听器的方式来触发审批动作

- **A（行动方案）**：

    1. **统一规范**：每个审批动作（按钮）为一个`{ permission: 按钮身份, handler: 业务逻辑, view: 弹窗 }`通过一个命令分发器去做分发，好处是**新增按钮 = 新增一个目录 \+ 一个 case 分支，**然后根据eventBus来触发不同审批动作逻辑

    2. **抽象公共能力**：我们将审批动作提交前，提交后、表单校验、意见输入校验、敏感词校验、成功回调、失败回调做了统一的能力抽象，生成每个高度独立的hook

    3. **值的存取\(Store设计\)**：之前在原有的基于Context传递大对象的是后有严重的性能瓶颈，顶层状态树过于庞大（包含流程节点、表单数据、权限、摘要详情等），任意微小字段变动都会触发 **Context 全局重渲染**，导致复杂表单页面操作卡顿，项目处于**遗留系统演进期**，无法引入重型第三方库（如 Redux/Zustand），且需兼容老旧的 `BpmPageContext` 生态，历史代码迁移成本必须可控。

    - 处理方式：

        - **底层存储与响应式订阅（**`**useStoreData**`**）**：

            - 放弃 `useState`，改用 `useRef` 存储状态结合 `Set` 实现发布\-订阅。

            - 封装 `useSyncExternalStore`（React 官方并发安全 API），配合 `lodash.isEqual` 深度比对，实现**细粒度 Selector 精准订阅**，从源头阻断无效渲染。

        - **命令式更新收口（**`**useDispatch**`**）**：

            - 统一封装 `dispatch` 方法，将 BPM 特有的“摘要详情（`summaryDetail`）”全量替换逻辑与普通字段的局部合并逻辑进行**内聚隔离**，让业务层调用更加语义化，不再散落冗余的合并判断代码。

        - **独创“非响应式”取值层（**`**useStoreValue**`\*\* \*\*\*\*\+ Proxy）\*\*：

            - 针对闭包陷阱痛点，我利用 `ES6 Proxy` 代理了 `get` 和 `set` 操作。该钩子**不触发组件订阅**，专门用于点击事件、`setTimeout` 和接口回调中获取绝对新鲜的数据。同时我在团队文档和代码注释中**明确标注了“禁止在渲染顶层解构”的 Lint 规范**，防止误用。

- **R（最终结果）**：

    1. **性能大幅提升**：重构后，非依赖字段变动时，无关组件重渲染次数降为 **0**；复杂联动表单的输入响应延迟从平均 **200ms\+** 降低至 **16ms** 以内（60fps）。

    2. **缺陷清零**：因闭包导致的历史数据错乱 Issue 全部关闭，提交和保存接口传参准确率达到 **100%**。

    3. **工程化收益**：**0** 新增 npm 依赖，构建产物无变化；核心 API 迁移成本极低，团队 **2 周内**完成了主要业务模块的平稳过渡，上线后至今 **0 线上事故**。

    4. **团队标准化**：将这套模式沉淀为部门内部的《BPM 状态管理最佳实践》文档，后续新开发的功能一律按此规范执行，显著降低了新人的状态管理心智负担。

### 2\. 本目录的架构落地说明（面试讲解用）

#### 2.1 目录结构

```
oa-approval/
├─ index.tsx                 工作台装配（Provider + 布局 + 桥接注册）
├─ types.ts                  动作协议 / 状态树 / dispatch / 中间件类型
├─ constants.ts              动作元数据、流程节点、人员、敏感词
├─ mock/initialState.ts      初始状态（permission 开关用于演示过滤）
├─ services/approvalApi.ts   模拟接口（耗时 + 可开关的失败）
├─ store/                    createStore / useStoreData / useDispatch / useStoreValue
├─ core/                     registry / eventBus / pipeline / middlewares / bridge
├─ actions/                  23 个动作，每个一个文件：{ permission, handler, view }
└─ components/               Toolbar / ActionModal / Form / Summary / Timeline / PerfLab
```

#### 2.2 难点一：20+ 审批动作的触发方式与 UI 强耦合

- 过去：每加一个按钮都要改 BPM 侧视图代码，新增动作 = 改 3 个仓库。
- 现在：动作收敛成协议 `{ permission, handler, view }`，动作文件只描述「弹窗长什么样 + 业务做什么」；
  `ActionModal` 是唯一视图宿主，按 `view.fields` 配置渲染表单。
- 新增一个动作只有两步：`actions/` 下新增文件 + 在 `actions/index.ts` 的数组里追加一项；
  工具栏、弹窗宿主、命令分发器零改动（注册表刻意显式注册，便于枚举和后续按需加载）。

#### 2.3 难点二：Context 大对象导致的全局重渲染

- 状态树含流程节点、表单、权限、摘要详情，任意字段变化都会让所有消费者重渲染，输入延迟 200ms+。
- 现在：Context 只放稳定的 store 实例；组件用 `useSyncExternalStore` + 稳定 selector + 等值比较精准订阅，
  `getSnapshot` 内部做快照缓存，派生值等价时返回旧引用，从源头阻断无效渲染。
- 页面每个卡片右上角的 `render ×N` 可直接对照：写无关字段 100 次，无关卡片计数不动。

#### 2.4 难点三：闭包陷阱导致提交参数错乱

- 异步回调里读到的是渲染时的快照。
- `handler` 拿到的是 `getState` 函数而非快照；取值层 `useStoreValue` 用 Proxy 代理 get/set，
  不订阅、也不怕闭包，专门用于点击事件、`setTimeout`、接口回调。
- 约束：禁止在渲染顶层解构取值层对象；需要驱动 UI 时改用 `useStoreData(selector)`。

#### 2.5 亮点一：公共能力 Pipeline

按 koa 中间件组织：`error → pending → permission → form → required → sensitive → beforeSubmit → handler`，
统一抽象了提交前/提交后、表单校验、意见必填、敏感词、防重复点击、成功/失败回调。
动作文件只写业务语义，新增动作不会漏掉权限或防重。

#### 2.6 亮点二：命令式更新 + 事件总线

- `dispatch` 把「摘要详情整包全量替换」与「普通字段局部合并」内聚隔离，业务层不再散落合并判断；
  摘要详情按 BPM 的 `groups[].items[]` 结构建模，`upsertItem(groupId, item)` 只做语义化局部更新。
- `transaction` 让 N 次写入只通知一次。
- 外部系统通过事件总线 + 桥接协议（`window.__OA_APPROVAL_BRIDGE__`）驱动动作，不依赖内部 hook，也不用跟着发版。

#### 2.7 结果与口径

无关字段变更时无关组件重渲染 0 次；复杂联动表单输入延迟 200ms+ → 16ms 内；
0 新增 npm 依赖（等值比较、深比较、事件总线均自研）；核心 API 迁移成本低，老页面可渐进式接入。
